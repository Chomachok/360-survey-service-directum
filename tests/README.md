# Автотесты Directum360 Feedback

API-тесты (REST, `requests`) и браузерные E2E-тесты (`Playwright`) сервиса опросов «360».
Набор собирается поверх уже поднятого окружения: backend, frontend и Mailpit запускаются
docker-compose'ом, тесты только ходят в них по HTTP.

Текущий результат полного прогона: **308 passed, 41 xfailed** (349 тестов, 2:21:
312 API + 37 браузерных).
`xfail` — это не «тест упал», а зафиксированный дефект продукта: ожидаем правильное поведение,
получаем текущее. Полный список — в конце документа.

Набор написан и проверяется на этой же кодовой базе: ветка `main`, коммит `90e420b`
(`feat: add tests`) — структура `backend/` + `frontend/`, вход по коду из письма
(`POST /api/auth/send-code` → `POST /api/auth/verify`). Под другие ветки или на другую
структуру проекта набор не адаптирован, и переносить его туда без правок нельзя.

## Подготовка

```bash
docker-compose up -d                 # backend :5223, frontend :8080, mailpit :8025/:1025
python3 -m pip install -r tests/requirements.txt
python3 -m playwright install chromium   # нужно только для E2E
```

Требования к окружению:

* backend должен быть доступен по `http://localhost:5223` (в `docker-compose.yml` проброс `5223:8080`);
* frontend — по `http://[::1]:8080`. На этой машине `127.0.0.1:8080` занят другим процессом,
  а nginx контейнера слушает IPv6, поэтому адрес по умолчанию задан в квадратных скобках.
  Если в вашем окружении frontend отдаётся на `127.0.0.1`, переопределите `WEB_BASE_URL`;
* Mailpit принимает письма на `:1025` и отдаёт их REST API на `:8025` — без него тесты входа
  не дождутся код подтверждения;
* в БД должны быть seed-сотрудники (`ivanov@…`, `petrov@…`, `sysadmin@directum360.ru`, …) —
  они создаются миграцией `AppDbContext`.

## Запуск

```bash
cd tests
python3 -m pytest                     # всё: api + e2e
python3 -m pytest api -q              # только API
python3 -m pytest e2e -q              # только браузерные
python3 -m pytest -m smoke            # критический минимум
python3 -m pytest -m "api and surveys"
python3 -m pytest api/test_rbac.py::TestRespondentCannotManageSurveys -q
python3 -m pytest --lf                # только то, что упало в прошлый раз
```

Отчёт: `tests/report.html` (пишется на каждом прогоне, `--self-contained-html`).
Полезные маркеры: `smoke`, `regression`, `api`, `e2e`, `auth`, `surveys`, `questions`,
`matrix`, `responses`, `results`, `templates`, `employees`, `rbac`, `contract`.

## Конфигурация

Адреса берутся из переменных окружения (по умолчанию — значения выше):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `API_BASE_URL` | `http://localhost:5223` | REST API backend'а |
| `WEB_BASE_URL` | `http://[::1]:8080` | интерфейс для E2E |
| `MAILPIT_URL` | `http://localhost:8025` | HTTP API почтового перехватчика |
| `HTTP_TIMEOUT` | `20` | таймаут запросов в секундах |

Для pytest есть те же опции командной строки: `--api-base` и `--mailpit-base`.

```bash
API_BASE_URL=http://10.0.0.5:8080 WEB_BASE_URL=http://10.0.0.5:8080 python3 -m pytest
python3 -m pytest --api-base http://localhost:5223 --mailpit-base http://localhost:8025
```

## Как устроены тесты

* `helpers.py` — клиенты `ApiClient` (JWT в заголовке) и `MailpitClient` (коды входа,
  письма-приглашения, ссылки), фабрики payload'ов (`survey_payload`, `question_payload`,
  `choice_question_payload`), окна дат (`draft_window`) и seed-сотрудники.
* `conftest.py` — фикстуры `admin_api` / `respondent_api` (токены кэшируются на сессию),
  `surveys` (`SurveyFactory`: черновик, вопрос, матрица, публикация, завершение, шаблоны,
  сотрудник + автоочистка), `ready_survey` (готовый к прохождению опрос).
* `e2e/conftest.py` — вход «в обход формы»: JWT получается тем же путём, что и в API-тестах,
  и кладётся в `localStorage` (`authToken`, `userName`, `userEmail`, `isAdmin`). Настоящий
  ввод кода проверяется только в `test_e2e_auth.py`, остальные сценарии так были бы слишком
  медленными. Хелперы `pick_employee` / `matrix_list_mode` / `switch_to_list_view` работают с
  `react-select` и тумблером режима матрицы.
* Данные тестов изолируются уникальным суффиксом (`unique_suffix()`) в названиях, email'ах и
  текстах вопросов. Это обязательно: опросы с ответами удалить нельзя (дефект `SURV-10`), поэтому
  в dev-БД копятся записи предыдущих прогонов, и поиск на дашборде по неуникальному названию
  начинает возвращать несколько карточек.
* E2E-тест, где участвуют два пользователя, открывает **отдельные контексты браузера**:
  `localStorage` привязан к контексту, иначе страница респондента затрёт сессию администратора.
* Дефекты помечаются `@pytest.mark.xfail(reason="ДЕФЕКТ <ID>: …", strict=False)` — маркер
  остаётся в коде до фикса, а прогон при этом зелёный. Если поведение исправят, тест станет
  `XPASS` и напомнит убрать метку.

## Ограничения набора

* Тесты рассчитаны на dev-окружение с SQLite и Mailpit и предполагают «грязную» базу:
  всё, что можно, убирается фикстурами, но опросы с ответами остаются (см. `SURV-10`).
* E2E не проверяют вёрстку и темы оформления — только поведение, доступное через
  доступные имена элементов (кнопки-иконки берут имя из `title`, `react-select` — из портала в `body`).
* Отправка писем при публикации асинхронная, поэтому проверки почты ждут появления письма
  в Mailpit с таймаутом, а не читают сразу.
* Набор нельзя запускать параллельно (`-n auto`) и в двух процессах одновременно: общий
  Mailpit (коды входа и приглашения) и одна dev-база, в которой тесты ищут свои сущности
  по названию.
* Данные одного прогона переиспользуются повторными прогонами: если почтовый ящик или база
  «переполнены» старьём, самый простой способ очистить окружение —
  `docker compose down -v && docker compose up -d` (удалит volume с SQLite).
